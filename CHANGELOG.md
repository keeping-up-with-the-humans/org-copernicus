# Changelog

## 0.2.0

### Upgrading from 0.1.0

What changes for a user of 0.1.0, in short. Each point names the entry below that describes it in full.

Stored files that this version refuses, and what to do:

- A run store of 0.1.0 that holds a text with a line break, a tab, a run of spaces or other whitespace between its words: a resume and the hybrid coder refuse that text, and so does a merge with a store of this version that holds it too; code such texts into a new store, or pass them with their whitespace collapsed (`copernicus.data.collapse_whitespace`) to continue the old coding (see **Texts as given**).
- A one-stage run store of 0.1.0 whose rubric file lists the levels of some marker in another order than from 5 down to 1, as the toy rubric does: a resume and a merge with a store of this version refuse it; code the texts into a new store, or list the levels of every marker from 5 down to 1 in the rubric file to continue the old coding (see **One-stage level order**).
- A run store of 0.1.0 coded under a model name that this version gives other capabilities, such as `maker/gpt-5-mini`: a resume and a merge with a store of this version refuse it, as the capabilities belong to the identity of a run; give the backend the capabilities that 0.1.0 used, such as `capabilities=ModelCapabilities()` for `maker/gpt-5-mini` (see **Model names behind a maker's prefix**).
- Text embeddings and reference embeddings whose recorded transformers versions belong to two major versions, such as 4.57.6 and 5.12.1, or to two epochs: every function that receives both refuses them; embed both sides in one environment (see **Texts and references of one load**).
- Text embeddings or reference embeddings whose description records a transformers or torch version that cannot be read as a version, such as `4.57.3oops`: the same functions refuse them; embed that side again with copernicus, or remove the key from a description written by hand (see **Texts and references of one load**).

Numbers that change:

- `long_short_split` counts a text whose covariate equals the median as long, the rule of the paper's analysis code, so a long-minus-short difference, the `long_short_difference` rows of `repeated_study` and `corrections estimate --long-short` can change when a text sits at the median of the covariate (see **Estimators**).
- `repeated_study`: the standard error of the cross-fitted estimator `ppi_crossfit` follows the study's `cluster` option as that of `ppi_identity` does, by default summing the contributions within each group whenever a group of a draw holds more than one labelled text, so its standard error can change under the default or `cluster=True` when groups hold several texts (see **Estimators**).
- `repeated_study`: `ppi_crossfit` now refuses a draw as `ppi_identity` refuses it, such as a draw with fewer than two labelled texts on a side of the difference, so a corpus whose draws often miss a side reports that row as `undefined_share_exceeded` instead of an estimate (see **Estimators**).
- The `pca` reduction of the similarity and the hybrid coder computes the first principal component exactly: where 0.1.0 let scikit-learn take a randomized SVD, as for some matrices with more than 500 rows or columns, the scores change by the error of that one random draw, and repeated runs agree; within a reduction, a row whose bytes an earlier row shares receives that earlier row's score, even where 0.1.0 used an exact decomposition, so its score can change in its last bits; a roll-up reduces the attribute scores as returned, so assigning equal rows one score can change every score of a later roll-up, including scores of texts whose rows are not shared; rounding changes in its input need not produce small score or rank changes when leading components are nearly tied or the sign anchor is near zero, and a roll-up whose input columns become constant is refused; a rank correlation computed on such scores can change (see **Deterministic principal component** and **One `pca` score for rows with equal bytes**).
- The standard errors of `ols_outcome_ppi`, `ols_predictor_ppi`, `oriv` and `stacked_2sls` can differ from those of 0.1.0 in their last digits, and on a nearly collinear design a standard error of 0, or one that looks implausibly small or large, may have been wrong in 0.1.0: recompute such a result (see **Standard errors of the regression estimators**).
- The one-stage prompt lists the levels of each marker in the order of the rubric file, so it changes for a rubric file that lists the levels of some marker in another order than from 5 down to 1 (see **One-stage level order**).
- The LLM coders send each text as the text table keeps it, with its line breaks, tabs and runs of spaces, so the prompt of such a text changes (see **Texts as given**).
- The encoder embeds each text as the text table keeps it, so the vector of a text with a line break, a tab or a run of spaces, and its hybrid score where it falls back to its own text, change under an encoder whose tokenizer tells whitespace apart, such as `gte_qwen2_7b`; a reference text is stripped at its ends before it is embedded (see **Embeddings of texts as given**).
- With a prediction constant on the labelled texts, `pseudo_values` reports `lambda_star` and `mean_rectified_tuned` as NaN, with reasons; the battery records them as null with those reasons, where 0.1.0 used weight 1 (see **An undefined tuning weight**).
- `strip_html` returns another text than 0.1.0 for some texts that hold `<` or `&`: a `<` outside a span that its rules accept now stays, with the text after it (`I <3 this film. <b>Great!</b>` gives `I <3 this film. Great!`, where 0.1.0 gave `I Great!`), and only character references closed by `;` are decoded (`Tom &amp Jerry` stays as it is, where 0.1.0 gave `Tom & Jerry`); a text without `<` and `&` comes out as before (see **The HTML helper limits which angle-bracket spans it removes**).

Calls that now stop with a reason:

- Power tuning with a prediction that is constant on the labelled texts, where 0.1.0 took the weight 1: `mean_ppi` and `group_difference_ppi` with `power_tuning=True` and `tuning_coefficient` raise `EstimatorError`, and `copernicus corrections estimate --power-tuning` stops with its message; estimate without power tuning, or with a prediction that varies on the labelled texts (see **An undefined tuning weight**).
- `validity_panel`: a score row of a scored text with a finite gold value that has no run number, or that holds an infinite score, stops the panel with an error that names the target and the text; give the row its run number or correct the score, or remove the text's gold value to leave the text out (see **Validity panel, broken score rows**).
- `construct_scores` of a numeric table with a row without a run number raises `ConfigurationError`, which names the texts, where 0.1.0 left the row out without notice; give every row its run number, or drop such rows (see **A row without a run number in `construct_scores`**).
- `moment_subtraction`, `simex` and `oriv` refuse a score whose line on the gold values rises over the labelled texts by at most 1e-12 of the score's range there, with the message that the score does not covary with gold; 0.1.0 refused only a covariance of exactly zero (see **Estimators**).
- Every call that loads the registered `gte_qwen2_7b` under transformers 5 or later stops with `ConfigurationError` before anything is downloaded or loaded; install the 4 line with `pip install "transformers>=4.56,<5"`, in an environment of its own if other models need transformers 5 (see **An encoder whose model code needs an earlier transformers line**).
- A tokenizer or a model that fails to load raises `ConfigurationError` from the original error, and the commands that load an encoder end with `error:` and exit code 1; code that caught the original error, such as an `OSError` for a model that is neither on the hub nor in the cache, catches `ConfigurationError` now and finds the original as its `__cause__` (see **A failed load of an encoder says what was being loaded**).
- A `pca` roll-up whose returned attribute scores are constant across the texts stops with `ConfigurationError`, as a matrix of constant columns did in 0.1.0; where equal rows now get one score, attribute scores that differed only by rounding residue become constant, so such a roll-up stops where 0.1.0 returned a component of that residue; the attribute scores then do not distinguish the texts (see **One `pca` score for rows with equal bytes**).
- `strip_html` of a value that is not a string raises `TypeError`, where 0.1.0 returned an empty string for `None` and every other empty value (see **The HTML helper limits which angle-bracket spans it removes**).

Installation:

- `tqdm` is no longer a declared dependency: no module of the package imports it (see **Dependencies**).
- `packaging>=22` is now a declared dependency: the encoder and the comparison of two loads read the versions of transformers and torch with its parser, and the `pca` reduction and the lasso and elastic net of supervised stacking read the version of scikit-learn with it (see **An encoder whose model code needs an earlier transformers line**).

### Changes since 0.1.0

- **Validity panel, one score per group.** `PanelSettings(unit="group")` and `copernicus validity panel --unit group` compare one score per group with the group's gold value, for a gold value that belongs to a group of texts such as a person who wrote several of them. A group's score is the mean over its texts that were scored for the target, each text's runs averaged first; a text never scored for the target does not enter, and `n_texts` counts the texts that did. The metrics and intervals are computed on the group rows, each group its own cluster of the bootstrap, and the noise on each group's mean score in the runs that all its texts have a score for. The setting needs a table with a group column whose ids neither merge nor split when written as text; a group that holds a text scored for the target with a finite gold value stops the panel when its texts with a gold value carry two values, scored or not, and so do a scored text with a gold value whose run-averaged score is not finite (no run with a score, or finite run scores whose average overflows) or whose covariate is missing or not finite, and a score row of a used text (a scored text with a finite gold value) without a run number or with an infinite score (see **Validity panel, broken score rows**), while a scored text without a gold value is dropped and counted as before. The panel frame gains the columns `unit` and `n_texts`; under the default `unit="text"`, on inputs whose run numbers are all present and whose input scores and any generated construct scores are finite or missing, every other value is what version 0.1.0 returned, and **Validity panel, broken score rows** says what changes on other inputs.
- **Texts as given.** A text table keeps each text as given, with only its ends stripped (`text.strip()`); version 0.1.0 collapsed every run of whitespace in it, line breaks included, to one space. The two-stage and the one-stage LLM coder send that text, so a text reaches the model with its line breaks, as in the paper's analysis code; their rule for texts under `min_chars` counts the characters of the text they send, and the text hash of a stored result is the hash of that text. `n_chars` and `n_words` still describe the text with every run of whitespace collapsed to one space, so their values, and the default covariate of the validity panel and of the corrections, do not change; the rule is `copernicus.data.table.collapse_whitespace` (also `copernicus.data.collapse_whitespace`), which the two-stage coder applies to its passages as before. A store coded by version 0.1.0 resumes, merges and feeds the hybrid coder as before for every text whose kept form equals its collapsed form, that is a text without a line break, a tab, a run of spaces or other whitespace between its words. A text whose kept form differs from its collapsed form has another prompt now, and so another hash than the stored one: a resume and the hybrid coder refuse it, and a merge refuses its id when two stores hold different hashes under it, as a store of version 0.1.0 and a store of this version do. Each message names the ids and what to do: code such texts into a new store, or pass them with their whitespace collapsed to continue the old coding.
- **Embeddings of texts as given.** The encoder embeds the text of a text table as the table keeps it (`Encoder.embed_table`, `copernicus embed texts`), with its line breaks, tabs and runs of spaces, and the hybrid coder embeds that text, not one with its whitespace collapsed, for a text under `min_words` and for a text without a verified passage; the passages of its evidence texts are as before. For a user of 0.1.0 the vectors of a text whose kept form differs from its collapsed form, and the hybrid scores of such a text where it falls back to its own text, therefore change for an encoder whose tokenizer tells whitespace apart, such as the byte-level tokenizer of `gte_qwen2_7b`. Each reference text is stripped at its ends before it is embedded (`embed_references`, `copernicus embed references`), which changes the vectors of references with whitespace at their ends only; reference sets are stored as before. The description of an embedding set made by an encoder records, from now on, `text_form` (`"as_given"`) and `texts_hash`, a SHA-256 digest over the SHA-256 digests of the embedded texts in row order; a subset leaves the digest out, and a description of 0.1.0, which holds neither key, loads as before.
- **One-stage level order.** The one-stage LLM coder lists the level descriptions of each marker in the order in which the rubric file lists the levels, as the paper's analysis code did; version 0.1.0 listed them from level 5 down to level 1 for every rubric. `Marker.level_order` holds that order (a marker built in code lists its levels in its `level_order`, by default from 5 down to 1, as before), and `Rubric.to_dict` writes each sub-rubric in it, while `Rubric.content_hash` does not see it, so the hash of every rubric stays what 0.1.0 computed and the stores and reference sets bound to a rubric stay bound to it. The extraction prompt of the two-stage coder still lists the levels from 5 down to 1 and its scoring rubric from 1 to 5. A one-stage store records the level order of every marker of every attribute (`level_orders` in its provenance) when the rubric lists the levels of some marker in another order than from 5 down to 1. For a user of 0.1.0: a one-stage store of a rubric whose file lists every marker's levels from 5 down to 1 resumes and merges as before; for a rubric file that lists the levels of some marker in another order, such as the toy rubric, which lists them from 1 to 5, the one-stage prompt has changed, and a one-stage store of version 0.1.0 is refused with a message that says so: code the texts into a new store, or list the levels of every marker from 5 down to 1 in the rubric file to continue the old coding. Two-stage stores are not affected.
- **Estimators.** The cross-fitted estimator of `repeated_study`, `ppi_crossfit`, takes the standard error of its pseudo-value column under the study's `cluster` option, with the choice that `ppi_identity` makes: by default the contributions of the texts are summed within each group whenever a group of a draw holds more than one labelled text, as in every draw of a corpus whose groups hold several texts, and `cluster=False` treats the texts as independent. Version 0.1.0 always treated them as independent. Under the default or `cluster=True`, the standard error and coverage of `ppi_crossfit` can change when groups hold several texts; neither is guaranteed to increase in a particular study. With `cluster=False`, this clustering change does not apply. With one text per group, `ppi_crossfit` keeps the standard error of 0.1.0 under the default and with `cluster=False`; with `cluster=True` its difference takes the clustered formula, as that of `ppi_identity` does. A clustered difference whose side of the corpus lies in one group, so that the side's contributions would cancel and leave its uncertainty out of the standard error, is refused on every draw that clusters, and its row is reported as `undefined_share_exceeded`: use a covariate that puts at least two groups on each side, or `cluster=False`. Before its column is cross-fitted, `ppi_crossfit` now refuses a draw as `ppi_identity` refuses it, with the same messages: fewer than two labelled texts for the mean, fewer than two labelled texts on a side for the difference (under every setting of `cluster`), and, when the draw clusters, fewer than two groups among its texts or its labelled texts; a draw that both the clustering rule and the cross-fit refuse now gives the reason of the clustering rule. Draws without two labelled texts on a side are therefore refused for the cross-fitted difference and counted in `n_undefined`, where version 0.1.0 returned the uncorrected value for that side (its cross-fitted predictions, when the side held no labelled text) or a value corrected by a single text, so a corpus whose draws often miss a side now reports that row as `undefined_share_exceeded` instead of an estimate with a large bias. The floor changes no number of a draw that holds two labelled texts on each side. The reverse calibration of `moment_subtraction`, `simex` and `oriv` refuses a score whose line on the gold values rises over the labelled texts by at most 1e-12 of the score's range there (`is_constant` applied to the line in units of the score's range, so the rule does not depend on the units of the score or of the gold values), with the message that the score does not covary with gold; 0.1.0 refused only a covariance of exactly zero, so a covariance that is zero up to rounding gave a meaningless slope from moment subtraction and SIMEX, and a refusal from ORIV that named another cause. `long_short_split` counts a text whose covariate equals the median as long (`covariate >= median`), the rule of the paper's analysis code; 0.1.0 counted it as short. The two sides are therefore the texts at or above the median and the texts below it, which ties can make unequal; a constant covariate leaves the short side empty, which the difference and the repeated study refuse. A long-minus-short difference, the `long_short_difference` rows of `repeated_study` and `corrections estimate --long-short` can therefore change when a text sits at the median of the covariate, as two texts of the toy corpus do.
- **Validity panel, broken score rows.** Under the default `unit="text"` too, a score row of a used text (a scored text with a finite gold value) without a run number stops the panel with an error that names the target and the text, on every route by which a target is built; version 0.1.0 averaged such a row into the text's score on a direct target and left it out of the generated construct, where a text whose rows all lacked a run number disappeared from the target without a count. A frame of target scores (with a `target_id` column) without a `run_number` column still counts every row as run 1, while a long attribute table without that column is refused, as in version 0.1.0, and a scored text without a gold value is dropped and counted as before, now also on the generated construct. An infinite score value of a used text stops the panel under both units and on every route, also where the generated construct would otherwise average `+inf` and `-inf` of two attributes in one run to a missing value (it now averages the finite attribute scores and keeps the infinite ones as the evidence of the refusal), and so does a used text's generated construct score that is infinite because the average of its finite attribute scores overflows. Under `unit="text"` this replaces what 0.1.0 did with such a text: it averaged the text's runs, leaving out a run whose construct score `+inf` and `-inf` had made missing, and dropped the text and counted it in `n_dropped_missing` when that average was not finite, while a text whose finite run scores overflow when averaged is still dropped and counted. Both refusals name the target, the text and, where the table has groups, its group. The infinite score is refused before the target's runs are averaged per text, and a missing run number before any metric is computed (under `unit="group"` after the checks of the groups), so that with warnings turned into errors the library's error, not numpy's warning about an average of `+inf` and `-inf`, stops the panel; under `unit="group"` too, an infinite run score is reported by this error, so within the panel the group unit's refusal of a run-averaged score that is not finite concerns a text with no run with a score or with finite run scores whose average overflows. A missing score (NaN) is admissible as before. Run numbers keep the values the frame gives them on every route: a column of pandas' nullable integer type that holds a missing value is no longer read as 64-bit floats, in which two run numbers above 2**53 could become one, so `n_runs` and the noise count every run. On inputs whose run numbers are all present and whose input scores and any generated construct scores are finite or missing, every value that version 0.1.0 returned is unchanged under the default `unit="text"`.
- **Model names behind a maker's prefix.** `capabilities_for_model` matches its prefixes (`gpt-5`, `o1`, `o3`, `o4`) against the part of the name after the last `/`, so a reasoning model named the way a router or a server names it, such as `maker/gpt-5-mini`, gets the capabilities of `gpt-5-mini`: no temperature, no `top_p`, and the `max_completion_tokens` field. The backend still sends the name as given, and an explicit `capabilities=` argument (`--backend-option capabilities=...` on the command line) still overrides the lookup. For a user of 0.1.0: such a name got the default capabilities, so `OpenAICompatibleBackend` sent a temperature and `top_p` that a reasoning model refuses; the capabilities belong to the provenance of a run and so to its identity, so a store coded by 0.1.0 under such a name does not resume or merge under this version unless the backend is given the capabilities 0.1.0 used (`capabilities=ModelCapabilities()`). A name without a `/` gets what it got before; a name whose part before the last `/` starts with one of the prefixes, such as `o3-maker/llama`, now gets the default capabilities.
- **Deterministic principal component.** The `pca` reduction of the similarity and the hybrid coder computes the first principal component by an exact decomposition chosen explicitly: `covariance_eigh` for a matrix of at most 1,000 columns and at least ten rows per column (with scikit-learn 1.5 or later, which has it), the full SVD otherwise. Version 0.1.0 let scikit-learn choose, which takes a randomized SVD drawn from numpy's global random stream for a matrix with more than 500 rows or columns, unless it has at most 1,000 columns and at least ten rows per column (with scikit-learn 1.5 to 1.9; with 1.3 and 1.4, for every matrix with more than 500 rows or columns), so that two runs on such a matrix gave different scores, as for a pole of several hundred texts against the pooled references of the hybrid coder. For a user of 0.1.0: for a reduction of the same input matrix, wherever the automatic choice was exact, each row that no earlier row equals byte for byte keeps its score bitwise, and a later row of such a group receives the first row's score (see **One `pca` score for rows with equal bytes**); where the automatic choice was randomized the scores are now the exact component, which differs from a stored score of 0.1.0 by the error of that one random draw, and repeated runs agree. A scikit-learn whose version cannot be read is refused by the `pca` reduction, with the advice to install a released version 1.3 or later.
- **The note of predictive mean matching.** `REGISTRY["multiple_imputation"].note_for("pmm")` says that the paper's battery fitted predictive mean matching beside the model draws, within the family, and that the library keys the draws to the row, so the random streams of both variants differ from those of the paper's battery; version 0.1.0 said that the paper's battery had removed the variant. Only the text of the note changes.
- **Dependencies.** `tqdm` is no longer a declared dependency: no module of the package imports it.
- **Documentation, the calls.** The calls that the pages show run as shown: the dry run of `copernicus references generate` with its required `--rubric`, `--out` and `--model`, the coder scores of `copernicus baseline ridge` with `--coder-score-column`, `--kind oriv` with `--score-a` and `--score-b`, embedding-augmented calibration with one embedding set through `encoder=`, and an OpenAI-compatible server of one's own with `api_key=`.
- **Documentation, the planner's numbers.** The planner's docstrings, the help of `copernicus corrections plan` and the pages say that `rho` is the Pearson correlation computed from the data. They say that `limit` is the upper limit of the multiplier and that the factor is a large-sample number. They describe `uncorrected_equivalent` as the machine-scored texts that one human-coded text is worth, not as the reciprocal. They name the model under which it holds: independent texts, a small association, and a human value, score and covariate that are jointly normal, with a score that is a line in the human value plus an error independent of the human value and of the covariate. With an error whose size depends on the covariate the number can differ.
- **Documentation, the planner's weight.** The factor is that of an estimator that gives the score the weight `cov(gold, score) / var(score)`. When some scored texts have no human value, the default weight 1 reaches the factor only when that slope is 1. When every scored text is human-coded, every weight gives the mean of the human values. Large-sample values from the formulas, which a test recomputes, illustrate the default weight in place of a simulation that could not be reproduced, and the pages state what the illustration assumes. The shortfall of a fitted weight, at most `1 / (n_human - 2)`, is stated with its model as an upper value.
- **Documentation, the planner for a regression coefficient.** A residual is what the linear fit on the regressors leaves unexplained, of the human value or of the score. For a coefficient of a regression with the construct as the outcome, the factor holds with the partial correlation, the correlation of the two residuals, when the prediction is the least-squares fit of the human value on the score and the regressors and when the mean squares of the two residuals and their mean product, at given values of the regressors, do not change with the regressors. Jointly normal human value, score and regressors satisfy this. It is not enough that each residual is, on its own, unrelated to the regressors. An error whose size depends on a regressor can make the corrected coefficient less precise than the human-coded sample alone.
- **Documentation, groups of texts.** The planner counts texts as independent and does not model the dependence of texts within a group. The pages say that what matters is the dependence, within a group, of what each text contributes to the estimate, and that a positive correlation of these contributions lowers the effective sample size; they no longer call the planned number a lower bound. The FAQ and the tutorials say that a standard error that treats the texts of a group as independent leaves out the covariance within groups and can be too small or too large.
- **Documentation, the paper.** What the pages of the hybrid coder, the validity panel, the NLP-ML baseline, the battery, multiple imputation and supervised stacking say about the accompanying methods paper and its analysis code is corrected: the paper measured noise within one configuration for the two-stage coder only, and its battery left out a correction's whole evaluation below a minimum number of human-coded texts, while the library's battery applies no such table but a correction still refuses what its own fit cannot use.
- **Documentation, other pages.** The decision guide says that its detection routes and sample-size results follow an earlier version of the paper. The FAQ shows the dry run's output under the character counter, which a test checks, and says that the estimate counts with the `o200k_base` encoding only when `tiktoken` is installed and the encoding can be loaded. The validity pages say how errors that change the order of the texts lower rank validity and that an exact reversal of the order keeps it at 1, and that an exact increasing linear function of the gold shows no level displacement and no calibration shortfall, where a decreasing one shows a shortfall.
- **Documentation, installing from the package index.** The README and the installation page say that `pip install org-copernicus` installs the package once a release has been uploaded to the package index, that none has been uploaded so far, and that until then the package is installed from its root folder or from a wheel built there; version 0.1.0 said that the command installs it once the first release is published. The release checklist says that a version can also be published as a commit and a tag of the public repository only, without the upload to the package index. For a user of 0.1.0 nothing changes: the package is installed from its root folder or from a wheel, as before.
- **Install hints, and the group unit's refusal of a run average.** When torch, transformers or vLLM is not installed, the error names first the command that works, `pip install ".[embed]"` (or `pip install ".[vllm]"`) from the package's root folder, and then `pip install "org-copernicus[embed]"` (or `"org-copernicus[vllm]"`) with its condition, once a release has been uploaded to the package index; version 0.1.0 named the install from the package index first and without that condition. The docstrings of `PanelSettings`, `validity_panel`, `compute_target` and `TargetResult` and the methods page of the validity panel say that the panel refuses an infinite run score of a used text with the error of broken score rows, under both units and before the runs are averaged, so that within the panel the group unit's refusal of a run-averaged score that is not finite concerns a text with no run with a score or with finite run scores whose average overflows; `reduce_to_groups` and `rows_per_group` of `copernicus.validity.panel_units`, which receive the run averages of their caller, refuse an infinite run average with that refusal. For a user of 0.1.0 only the text of the two install messages changes.
- **Documentation, the repeated study.** The repeated study, the draw of the human sample and their pages no longer say that the intervals are conservative at large sampling fractions: no finite-population correction is applied, which can make them conservative but does not guarantee it; a whole-group draw that misses a group holding a large share of the texts can leave a ratio bias and an interval that covers far less often than 95 percent although every draw is defined; and a row's status `ok` certifies only that the share of undefined draws is within the limit. The study's docstring says that the variance of the machine term is absent over draws from a fixed corpus only for `ppi_identity`, whose score is fixed before the draw, while `ppi_crossfit` learns its prediction on each draw.
- **Departures from the paper's analysis code.** Every methods page of a method that the paper's analysis code also has lists the known departures from that code, and a test keeps the list of these pages and checks that each entry holds at least eight words and no placeholder. Added to the lists: on the validity page, how the paper's figure of the score errors of the two-stage coder differs from the panel's definition, and by how much; on the baseline page, the keys of the random generators, by which the paper's seeds give other folds and draws, the mean over seeds and the thread count; on the correction pages, the floor of 50 defined bootstrap resamples with the defaults of `simex`, the random streams of three families, the weights of a stacked embedding set, the predictions of the drawn texts in multiple imputation, the three labelled texts that the best score column needs, the battery's constant training range, the start of the principal-axis iteration, now described correctly, and the ensemble's error metrics; on the coder pages, the text sent as given with the cleaning of markup as the user's step, the stop above a 10 percent failure share and the text ids of the wording seed; on the hybrid and the similarity page, the fallback text, one vector per string and the `pca` route, whose condition is now stated exactly. - **An undefined tuning weight.** Power tuning refuses a prediction that is constant on the labelled texts by the library's rule `is_constant` (a range of at most 1e-12 times the larger of 1 and the largest absolute value), where the tuning weight `cov(gold, prediction) / var(prediction)` is undefined: `mean_ppi(..., power_tuning=True)` and `group_difference_ppi(..., power_tuning=True)` raise `EstimatorError` with a message that names the estimator, the prediction and the labelled rows and says what to do, `copernicus corrections estimate --power-tuning` stops with that message and writes no output file, and `copernicus.corrections.families.pseudo.tuning_coefficient` raises `EstimatorError` as well, also when it is given no labelled row. `pseudo_values` reports `lambda_star` and `mean_rectified_tuned` as NaN for such a prediction and logs a warning. Version 0.1.0 took the weight 1 there, so a power-tuned call returned the untuned estimate under the tuned method's name, and `pseudo_values` a tuned mean computed with the weight 1. For a user of 0.1.0: such a call now stops; estimate without power tuning (`power_tuning=False`), or with a prediction that varies on the labelled texts. This correction leaves every estimate without power tuning, every power-tuned estimate whose prediction varies on the labelled texts, the pseudo-value column and `mean_rectified` as they were; the weight keeps its definition, with no floor and no cap.
- **Standard errors of the regression estimators.** `ols_outcome_ppi` and `ols_predictor_ppi` compute the covariance of their coefficients from each text's contributions transformed by the moment matrix (one solve per text and term) instead of multiplying out the inverse moment matrix, the covariance and the inverse again, and the stacked two-stage system of `oriv` and `stacked_2sls` computes its text-clustered sandwich from the score rows transformed in the same way. A variance computed so is a sum of squares, so rounding can no longer make it negative, as it could the diagonal of the multiplied-out product, and nothing is clipped to zero. For a user of 0.1.0: on a nearly collinear design that product could lose its digits, so a standard error of 0 (a negative diagonal clipped to 0) or one that looks implausibly small or large may be wrong; recompute such a result. A standard error of 0 remains right when the transformed contributions do not vary, as in a perfect fit. An accepted design that is poorly conditioned can have a large standard error, and a design whose moment matrix is not clearly positive definite is still refused. On other designs the numbers can differ in their last digits: on seeded designs of both regression estimators, both variants, with and without clustering and covariates, and of the stacked system, the largest relative difference was of the order of 1e-15. The details of both regression estimators hold the new `condition_number`, the condition number of the moment matrix scaled to a unit diagonal, and a warning is logged when it exceeds `1 / sqrt(machine epsilon)`, about 6.7e7: the scaled matrix is then nearly singular, so the solve can lose more than half of its digits, and the warning names the causes to check, a regressor that is nearly a combination of the others and, for `ols_predictor_ppi`, the subtraction of the labelled texts' moments leaving little of the construct's variance. The refusal of a stacked system whose instrument matrix is rank-deficient (`oriv`, `stacked_2sls`) gives the computed rank and names the two causes to check, a measurement that does not vary and two measurements whose sizes differ by many orders of magnitude; version 0.1.0 said only that a measurement was constant.
- **An encoder whose model code needs an earlier transformers line.** `EncoderSpec.transformers_below` names the first version of transformers with which an encoder's own model code, the code of its revision, does not load: a release number such as `"5"`, above 4.56, the lower bound of the `embed` extra; another value is refused with `SettingsError`. When an encoder is asked to load, before anything is downloaded or loaded, it reads the installed transformers version whole, with the parser of the `packaging` library (now a declared dependency of the package), and compares it with that version, by its epoch and then by its release numbers, so that a pre-release or local build of the 5 line counts as the 5 line and a version of another epoch is not below the bound; an installed version that the parser cannot read is refused for an encoder with a bound. The registered `gte_qwen2_7b` sets it to `"5"`: the model code at its pinned commit reads the configuration attribute `rope_theta`, which transformers 5 no longer provides on the configuration object (it moved into `rope_parameters`), so with transformers 5 its load fails inside the model's code. For a user of 0.1.0: under transformers 5 or later, every call that loads `gte_qwen2_7b` (`Encoder.embed` and `Encoder.embed_table`, `embed_references`, `score_hybrid`, and the commands `copernicus embed texts`, `copernicus embed references` and `copernicus hybrid score`) now stops with `ConfigurationError`, which names the encoder, the installed version, the reason and the remedy: install the 4 line with `pip install "transformers>=4.56,<5"`, in an environment of its own if other models need transformers 5. The `embed` extra keeps its lower bound and gets no upper bound, since the three other registered encoders load under transformers 5; a specification without the field, such as the one built for a Hugging Face id, loads as before, and importing the library or listing the encoders still imports no transformers.
- **A failed load of an encoder says what was being loaded.** When the tokenizer or the model of an encoder fails to load, inside transformers or inside the model repository's own code, the encoder raises `ConfigurationError` from the original error, with a message that names the encoder, its model id and revision, whether the repository's own code was allowed, the installed transformers and torch versions, and the type and text of the original error. For a user of 0.1.0: such a load raised the original error itself, such as an `OSError` for a model that is neither on the hub nor in the cache, or an `AttributeError` from the model's own code; code that caught those errors around `Encoder.embed`, `Encoder.embed_table`, `embed_references` or `score_hybrid` now catches `ConfigurationError` and finds the original error as its `__cause__`, and the commands `copernicus embed texts`, `copernicus embed references` and `copernicus hybrid score` end such a load with `error:` and the message and exit code 1, where they ended with the original error's traceback. The load still fails, nothing is retried, and an interruption such as `KeyboardInterrupt` passes as before.
- **Texts and references of one load.** Every function that receives a text embedding set and reference embeddings compares the two loads of the encoder in one check: `score_similarity`, `score_similarity_many`, `run_grid`, the pole scorer `copernicus.similarity.poles.PoleScorer`, `score_hybrid`, `scoring_provenance` and the commands `copernicus similarity score` and `copernicus hybrid score`; the arithmetic kernel `per_reference_similarity`, which receives the reference vectors as an array, checks nothing. The check compares the identity of the encoder (refused as before, now with the advice to embed both sides with one encoder specification), the loaded commit (refused as before when both sides record one), and the transformers versions that both sides record, each read whole with the parser of the `packaging` library. For a user of 0.1.0: texts and references whose recorded transformers versions belong to two major versions, such as 4.57.6 and 5.12.1, or to two epochs are now refused with `ConfigurationError`, which names both versions and says to embed both sides in one environment; `run_grid` refuses a key of two loads before it scores any key, with the key at the start of the message; a `PoleScorer` refuses them when it is built; and the hybrid coder refuses references of another load before its embedding pass when its encoder is the library's `Encoder` (an encoder object of one's own after the pass). Two readable versions of transformers of one epoch and one major line, two readable versions of torch, and a side whose sidecar records no version (a set built by hand; every set that the encoder of 0.1.0 made records both) are scored with the same scores and a warning that the pole scorer of the scoring call logs once (logger `copernicus.similarity.poles`); the provenance of the scores records the transformers and torch versions of both sides as recorded (`"unknown"` for a version not recorded) and the warnings under `load_comparison`, in `scoring_provenance`, `HybridResult.provenance` and the description files of the two commands, so it shows the versions compared, or that a comparison was not possible. A recorded version that the parser cannot read, such as `4.57.3oops` or a value that is not text, is refused, also when both sides record the same text or the other side records none, and `scoring_provenance` refuses inputs of two loads as scoring does. The storage format of 0.1.0 stays readable, and compatible pairs keep their scores.
- **The HTML helper limits which angle-bracket spans it removes.** In `copernicus.data.strip_html` a literal `<` is removed only as part of a span that the cleaning rules accept; the function's documentation gives the rules in their order, with their exceptions. Version 0.1.0 removed everything from a `<` to the next `>`, so a `<` outside such a span now stays, and the text after it is no longer removed with it: `I <3 this film. It is > all the rest.` gave `I all the rest.`, `a < b and c > d` gave `a d`, and `Dear <name of the guest>, welcome.` gave `Dear , welcome.`; each now comes back unchanged. Plain text in the form of an accepted tag is still removed, as in 0.1.0: an element name, alone or with a word that may stand as an attribute without a value, such as `<A>`, `<time>` or `<i open>`, a word with a hyphen such as `<well-known>`, and two words joined by a colon such as `<Note:important>`. The rules for line breaks, paragraphs, divisions, block quotes, lists, headings, images and links read whole element names, so `<lipstick>` no longer starts a list item and `<ultimate goal>` no longer becomes a line break. An image's text now needs an `alt` attribute written in lower case with its value in double quotes, so `<img data-alt="cat">`, which gave `cat`, now gives nothing. A `>` inside a quoted attribute value or inside a comment no longer ends the tag or the comment. The delimiters of a doctype, a processing instruction and a CDATA section, which 0.1.0 removed, stay, while their contents are cleaned like any text, so `<![CDATA[<b>word</b>]]>`, which gave `word ]]>`, now gives `<![CDATA[ word ]]>`, and a tag with an attribute without a value that is not on the rule's list, such as `<div data-flag>`, stays text. Complete `svg` and `math` elements are cleaned by a step of their own: `<svg><svg/><text>Hello</text></svg>`, which gave `Hello`, now gives `<text>Hello</text>`, and the function's documentation gives the exceptions of that step. Only character references closed by `;` are decoded: 0.1.0 also turned the `&copy` of `?a=1&copy=2` into `©`, `Kind&regards` into `Kind®ards` and `&notaname;` into `¬aname;`, which now stay as written. A value that is not a string raises `TypeError` with a message that says so; 0.1.0 returned an empty string for `None` and every other empty value and raised the `TypeError` of `re` for the other values. On a long run of `<` or of unclosed comment openers, where 0.1.0 needed time that grows with the square of the length, the time now grows linearly with it. A text without `<` and `&` comes out as before.
- **A row without a run number in `construct_scores`.** `copernicus.coders.construct_scores`, the construct score per text and run of a numeric long table, refuses a row whose run number is missing with `ConfigurationError`, which names the texts of such rows (the first ten) and says what to do: give every score row its run number, or drop such rows to leave their scores out. Version 0.1.0 grouped the rows by run number, which left such a row out without notice, and with it a text whose rows all lacked a run number. Every row of a run store written by the library holds its run number, so the exports of a store (`export_construct_scores`, `export_text_scores`, `copernicus store export`) are not affected. The validity panel builds the construct from the rows that have a run number and refuses a row without one for a scored text with a finite gold value, under both units, where version 0.1.0 averaged such a row into a direct target or left it out of the generated construct (see **Validity panel, broken score rows**); `copernicus.validity.panel_inputs.resolve_target_scores` leaves such a row out of the construct it returns, as version 0.1.0 did.
- **The refusal of too few values.** `plugin_value` and `naive_se` of `copernicus.corrections.estimates` refuse too few values with a message that gives their number and says to provide more, or, for the values on two sides, gives the number on each side and says to provide more on the side with too few or to choose another grouping; version 0.1.0 spoke of the values in each group in both cases. `group_difference_ppi` words its refusal of too few labelled texts on a side of its grouping in the same way: it speaks of labelled rows on each side, gives the smaller of the two counts and says to label more texts on that side or to use another grouping, where version 0.1.0 said that the difference needs labelled rows in each group. Only the texts of these messages change.
- **One `pca` score for rows with equal bytes.** The `pca` reduction (`reduce_matrix` with `"pca"`, used by the similarity and hybrid coders for poles and roll-ups) gives rows with equal bytes one score: the score of the first of them in the order given. It compares the input rows before standardisation, with no tolerance; a one-bit difference, including `-0.0` versus `0.0`, keeps two rows distinct. Equal embedding vectors alone do not guarantee equal cosine bytes. For a reduction of the same input matrix, each row that no earlier row equals keeps its signed decomposition score bitwise. Grouping runs after decomposition, sign selection and refusal checks and changes none of those operations for that matrix. A one-column matrix is returned unchanged. A roll-up reduces the attribute scores as returned: `rollup_scores` of those scores gives the returned roll-up. Assigning equal rows one score can change the input of a later roll-up in its last bits, even when all upstream decompositions are exact. Every score of that roll-up can then change, including scores of texts whose rows are not shared. These changes need not be small when leading components are nearly tied or the sign anchor is near zero; ranks of different rows can reverse by much more than rounding. If the returned attribute columns become constant, the roll-up is refused, even when rounding residue previously let it return scores. This is separate from the change from randomized to exact decomposition described above. Version 0.1.0 and the paper's analysis code returned the sign-anchored decomposition scores without grouping equal rows, so equal input rows could receive different last bits and rank correlations could treat them as untied. Recompute roll-ups and their rank correlations when upgrading; the departure lists of both coders describe these differences.
